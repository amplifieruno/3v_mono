# ITAP Data Layer — Design

Date: 2026-10-18
Status: draft v2 (after builder check and three review passes: coverage, Hasura/Postgres feasibility, modeling consistency)

## 1. Intent

ITAP is a demo of an identity tracking and access platform (`docs/base/*`, `docs/stages/SA_2..SA_6`). The admin UI will be rebuilt on burojs 0.5 once it is released. Before that, we build the **data layer**: the complete Hasura/Postgres model, permissions, and the server-side logic (SQL functions, triggers, crons, actions) that makes the platform behave.

The bar is **a logically correct, well-architected project** that a reviewer would recognise as a real platform's data layer, covering every entity in the docs and all stages. The UI is put on top afterwards; the data layer is the part that matters now.

Why: the demo will be clicked by the customer and recorded on video. Every screen in the docs must be able to look like it works, so the data behind it must exist, be related correctly, be produced by real logic where an action happens, and be populated with believable data.

## 2. Goals

1. Hasura schema covering every entity in the docs (≈85 tables, §6), with fields, types, constraints, indexes, relationships.
2. Multi-tenancy by **organization** from day one, enforced declaratively in the database and in Hasura (§4).
3. Permissions in Hasura metadata for the roles in §5, with no cross-organization path through tables, functions, actions, storage or audit.
4. Server-side logic that reacts to **real** events (camera detections, user actions) and periodic work (§8).
5. A seed producing a believable **office center** scenario (§9), files included, timestamps relative to seed time.
6. Live camera face recognition keeps working on the new schema (§7).
7. The UI calls everything through Hasura: CRUD, tracked SQL functions (queries and mutations), and Actions (backend) where an external service is involved.

## 3. Non-goals and anti-goals

**Non-goals (this phase):**
- Any UI work. The current admin-ui will break against the new schema; accepted (it gets replaced).
- Activity simulation. No background generator of events. Data comes from the seed and real actions (cameras, users). Consequently: estimated positions during camera gaps exist only in seeded history (no live estimator).
- Role differentiation inside an organization. One role (`org_admin`); schema ready for more (§5).
- Support portal, knowledge base, tickets, training, competency, test dashboards (SA_4). Possibly a separate app.
- Real email/SMS/push delivery, real HR/ERP/SIEM/BMS connectors, real SLA/cost monitoring, real liveness/anti-spoofing. Represented by data and stubbed handlers (§8.5).
- Multi-stage verification chains (single approval step), general (non-face-auth) API keys and rate limiting, evacuation roll-call records (evacuation view = live occupancy during an `evacuation` override).
- Platform super-admin UI. Organizations and members come from the seed.
- Keeping the existing 19 migrations or existing data (dev and prod DBs are recreated).

**Anti-goals (failure even if it "works"):**
- Tables with no relations or logic behind them. Every table is connected to the model, justified by a doc section, and either written by a user flow or by logic in §8.
- Cross-organization data leakage through any role, relationship, function, action, storage path or audit row.
- Breaking live recognition (cameras → identities → detections).
- Business logic in the UI. If a rule exists (segment membership, occupancy, escalation), it lives in the data layer.
- Bending the model to the UI framework (owner decision): relations are FKs and junction tables, not id arrays or ids inside JSON.

## 4. Tenancy, authentication, storage

### 4.1 Organizations and declarative isolation
- `itap.organizations` is the tenant. Every business table has `organization_id uuid not null`.
- Every business table has `UNIQUE (organization_id, id)`. **Every FK between business tables is composite**: `(organization_id, x_id) → parent(organization_id, id)`. The database therefore makes it impossible to reference another organization's row from any table, including sideways references and junctions. Where the deletion policy (§6.0) says SET NULL, it is `ON DELETE SET NULL (x_id)` (PG15+), so `organization_id` is never nulled.
- Exception: links **between high-volume log rows** (`events.detection_id`, `identity_locations.detection_id`, `notification_deliveries.event_id`, `webhook_deliveries.event_id`, `incident_events.event_id`, `search_results.search_request_id`) are plain indexed uuid columns without FK. Logs are written only by trusted SQL in the same organization, and retention then deletes logs without cascading row-by-row updates across other logs. Real FKs are kept to stable entities.
- `UNIQUE (organization_id, id)` exists only on tables something references.
- **Every FK column set is indexed** (leading with `organization_id`); Postgres doesn't do it automatically, and deletes/cascades depend on it.
- `organization_id` → `organizations(id)` itself: `ON DELETE CASCADE`.
- Same-facility consistency uses the same technique where it matters: `areas.parent_id`, `floor_plans.area_id`, `access_points.area_id/from_area_id`, `devices.area_id` carry `facility_id` in a composite FK `(organization_id, facility_id, x_id)`.
- File references (`*_file_id → storage.files`) cannot be composite; a trigger checks `storage.files.bucket_id = organization_id::text`.

### 4.2 Users and membership
- Users are Nhost `auth.users` (email + password). No duplicate user table.
- `user_settings` (1:1 with auth.users, cross-org personal preferences only): locale, timezone, last_organization_id. Anything that involves other people of an org (vacation delegate, quiet hours for escalations) lives on `organization_members`.
- `organization_members`: organization_id, user_id, role (enum, currently only `admin`), status (`active/suspended/deactivated`), title, department, joined_at, expires_at, deactivated_at, deactivated_by, quiet_hours (windows, §6.0), vacation_until, vacation_delegate_user_id (composite FK to a member of the same org). `UNIQUE (organization_id, user_id)`.
- **Every column referencing a user inside an org** (assignees, authors, approvers, recipients, owners, `created_by`) is a composite FK `(organization_id, user_col) → organization_members(organization_id, user_id)` (the workspace-member pattern): a user from another organization can never be assigned, notified or shown.
- **Members are never hard-deleted while referenced; they are deactivated.** FKs to members use `ON DELETE NO ACTION` (checked at statement end, so an organization cascade still removes members and their references in one statement; `RESTRICT` would fail there). History keeps resolving to the person ("deactivated").
- Trigger `active_member_check`: assignment/recipient columns may only be set to an `active` member (checked only when the column changes; existing references stay).
- On deactivation: the member can no longer switch into the org; their subscriptions and inbox stop receiving deliveries (rows kept); `vacation_delegate_user_id` receives escalations if set.
- Account removal (e.g. GDPR erasure of a platform user) = disable and anonymize the `auth.users` row, never delete it; `organization_members.user_id → auth.users` is `NO ACTION`.

### 4.3 Two-token flow (owner decision)
1. Login via Nhost → **base token**, role `user`: own `user_settings`, own memberships with organization name/logo, Action `switch_organization`.
2. `switch_organization(organization_id)` → backend checks an active membership and signs an **organization token** with the key and issuer from Hasura's `JWT_SECRET` (`HS256`, `iss: "hasura-auth"`, claims under `https://hasura.io/jwt/claims`):
   - `x-hasura-user-id`, `x-hasura-organization-id` (lowercase uuid text), `x-hasura-default-role` (`admin` → `org_admin`), `x-hasura-allowed-roles` = [`org_admin`] (slice-1 fix wave: an org token cannot act as `user`, so it cannot call `switch_organization` to renew itself).
3. TTL 15 min, renewed by calling the action again with the base token (the action is granted to `user` only and rejects disabled accounts). Revocation effective within TTL. The switch is recorded in `audit_log` (`switch_org`).
4. The same token works with hasura-storage (it forwards the Authorization header to Hasura, which evaluates `storage.files` permissions). Verified by one upload test early in delivery.
5. Fix `apps/backend/.env` (malformed `HASURA_JWT_SECRET`, wrong `JWT_SECRET`); the signer parses `key` and `issuer` from the same JSON Hasura uses.

### 4.4 File storage
- **One Nhost Storage bucket per organization**, bucket id = organization id (text), created by trigger on `organizations` insert (`ON CONFLICT DO NOTHING`, reseed-safe).
- `storage.files` for `org_admin`: insert/select where `bucket_id = X-Hasura-Organization-Id`; **no delete** (deletes go through Action `delete_file`, which uses the storage API). Insert check rejects sensitive kinds (`metadata.kind in ('profile_document','dsr_export','auth_capture','export')`, the list of `itap.sensitive_file_kinds()`), so only backend Actions (`upload_profile_document`, DSR, auth, exports) can create them; select excludes them. Because hasura-storage 0.7 inserts the row as the caller without metadata and writes `metadata` afterwards with the admin secret, the BEFORE trigger `itap.storage_files_sensitive_kind_guard` on `storage.files` enforces it on the upload path too: a sensitive kind (`itap.sensitive_file_kinds()`, now incl. `export`) is refused under a non-admin role or when it is set on a row a member uploaded (`uploaded_by_user_id` present). Sensitive files are opened through Action `open_file(file_id)` that returns a short-lived URL and writes `audit_log` `view_sensitive`.
- All crops, photos, documents, reports, exports go to the org bucket with `metadata.kind`.
- Organization logos live in a shared bucket `org-logos` (not sensitive), selectable by `user` and `org_admin`.
- Files are deleted only through the hasura-storage API (backend), never by deleting `storage.files` rows, so MinIO objects don't leak (retention, reset, org delete).

## 5. Roles

| Role | Who | Access |
|---|---|---|
| `public` | unauthenticated | nothing |
| `user` | logged in, no org selected | own `user_settings`, own `organization_members` (+ org name/logo), Action `switch_organization` |
| `org_admin` | admin of current org | CRUD within `organization_id = X-Hasura-Organization-Id`, except **ro** columns/tables and secret columns |
| backend | handlers, crons | admin secret **plus forwarded caller headers** (§8.0) |

Conventions for `org_admin`:
- select/update/delete filter `{organization_id: {_eq: X-Hasura-Organization-Id}}`; `allow_aggregations: true` on every select.
- insert presets: `organization_id = X-Hasura-Organization-Id`, `created_by = X-Hasura-User-Id`.
- **ro** columns (counters, computed state, timestamps, embeddings) excluded from insert/update; append-only logs select-only.
- **Secret columns** (device passwords, integration secrets, webhook secrets, key hashes, invitation token hashes) are writable but excluded from select via column permissions, and redacted from `audit_log`.

Future roles: SA_4 §2.1.4 six roles + FS scopes. Adding a role = enum value + Hasura role permissions + mapping in `switch_organization`. Facility ABAC would add an `organization_member_facilities` table and an `x-hasura-facility-ids` claim — additive, not built now.

## 6. Data model

Schema `itap`. Nhost `auth.*`, `storage.*` used as-is. Function result tables in schema `itap_results` (§8.1).

### 6.0 Conventions
- PK `id uuid default gen_random_uuid()`; `UNIQUE (organization_id, id)`; composite FKs (§4.1). Junction tables also carry `organization_id`.
- Codes (`IDENTITY-12345` etc., FS): `number bigint` per organization per table from `organization_counters` via `INSERT … ON CONFLICT DO UPDATE … RETURNING` (concurrency-safe); `code text GENERATED ALWAYS AS (prefix || lpad(number::text, 5, '0')) STORED`, unique per org, indexable and a flat column for the UI. On: identities, profiles, segments, facilities, devices, reports, notification_rules, incidents, access_policies, event_rules, client_applications, visits.
- `created_at`, `updated_at` (trigger) on every table (`updated_at` also drives burojs live updates); `created_by` where a human creates rows.
- Enums: Hasura enum tables `itap.<thing>_<kind>s (value text pk, description)`, lowercase snake values (matches docs; `.claude/rules/hasura-conventions.md` updated).
- Hasura enum tables can only have the key and one text column, so they are exempt from timestamps. **Ordered enums** (severity, profile access level, area access level, priority) get a rank via one immutable SQL function per scale (`severity_rank(text)` etc.); comparisons always go through it. Profile and area access levels keep their doc vocabularies but share one 1–4 rank scale, so "area level above profile clearance" is defined.
- Enum *sets* (a rule's channels, an app's modes and allowed attributes) are junction tables to the enum table, like any many-to-many (a CHECK cannot validate array elements against a table).
- Append-only tables (detections, locations, events, decisions, attempts, deliveries, audit, metrics) have `created_at` only, no `updated_at` trigger.
- **Time**: all timestamps `timestamptz`. Hourly buckets are UTC `timestamptz`; daily buckets are `date` in the facility's timezone (organization timezone for org-wide stats). Schedules are wall-clock windows evaluated in the timezone of the place they apply to (facility), with one JSON window shape `[{days:[1..7], from:'HH:MM', to:'HH:MM'}]` and one function `in_windows(windows, tz, ts)` used by operating hours, work schedules, segment schedules, access policy schedules and quiet hours.
- **GraphQL names**: tables live in schema `itap` (separate from Nhost `auth`/`storage`); every table gets `custom_name` (and root field names) without the `itap_` prefix in metadata, generated, not hand-written.
- Files: `*_file_id uuid → storage.files`, bucket check trigger (§4.1). No inline base64.
- Geo: facility `latitude/longitude numeric` (no PostGIS). Shapes in floor-plan pixel space as GeoJSON-like jsonb (`Polygon` or `{type:'Circle', center, radius}`).
- `custom_fields jsonb` validated against `custom_attribute_definitions` by trigger.
- **Deletion policy** (one rule per kind of reference):
  - *People and anything history points at* (members, profiles, identities, devices, facilities, areas): lifecycle by status (`deactivated/archived/terminated/merged`), not by delete. Hard delete only when nothing references the row (`NO ACTION`), or through the retention/erasure flows that anonymize or detach first.
  - *Configuration and reference data* (rules, templates, groups, policies, segments, companies, schedules): `NO ACTION` from referencing configuration; archived via status when in use.
  - *Owned children* (junction rows, steps, notes, versions, photos, embeddings): `CASCADE` from the owner.
  - *Logs and history* (detections, locations, events, decisions, attempts, deliveries, search results) referencing identities, profiles, devices, files or detections: `ON DELETE SET NULL (col)`, so retention and erasure can remove sources without losing the log row.
  - *Organization*: `CASCADE` to everything; constraints between business rows are `NO ACTION` (not `RESTRICT`) so the cascade completes in one statement.
- **Array exceptions** (never edited by forms): system caches (`areas.path`, `tracking_sessions.areas_visited`). Everything else, including polymorphic targets, uses typed nullable FKs with an exactly-one CHECK plus a partial unique index per branch.
- **JSON exceptions that contain ids**, each guarded: segment and notification-rule `conditions` (a rule language; a validation trigger checks every referenced id belongs to the org and that referenced segments are manual), and `identity_merge_moves (entity, row_id)` (an undo log, written and read only by merge functions).
- **Versioned entities** (access policies, event rules) use one pattern: a header row (identity, `current_version_id` = what is enforced) + version rows (`draft/pending_approval/published/superseded`) that own their children (subjects, targets, scopes). Editing = editing the draft version; publishing = flipping `current_version_id`; rollback = publishing an earlier version. Decisions and events reference the version that produced them.
- **Ids inside JSON**: never for references. JSON is used for shapes, layouts, rule parameters, payload snapshots.
- burojs `@burojs/hasura` alignment: one table per resource, flat columns, `_by_pk`, `_aggregate { count }` (hence `allow_aggregations`), many-to-one via FK columns, many-to-many via junction tables (burojs gains support, Linear REF-36), aggregates beyond count via `_aggregate` in custom queries or tracked functions.

**ro** = system-managed; **secret** = writable, never selectable.

### 6.5 Segments (FS §4, SA_3 §2.1.3)
| Table | Key columns | Notes |
|---|---|---|
| `segments` | number, name, description, color, icon, kind (`manual/dynamic`), target (`identities/profiles`), conditions jsonb, status (`active/inactive/archived`), active_from, active_until, schedule jsonb, member_count **ro**, last_evaluated_at **ro**, last_evaluation_error **ro**, last_evaluation_failed_at **ro**, template_id | `kind` and `target` are immutable after creation. Manual: `conditions = '{}'`; dynamic: conditions required. `schedule` NULL or `[]` = no restriction. Template FK `(organization_id, template_id, target)` (template of the same target) `SET NULL (template_id)`. A segment named by another segment's/template's condition, an event rule scope or a notification rule cannot be deleted. |
| `segment_members` | segment_id, target, identity_id, profile_id, source (`manual/rule`), added_by, added_at, removed_at, removed_by | Exactly one of identity/profile, consistent with `target` (CHECK); FK `(organization_id, segment_id, target) → segments(organization_id, id, target)` makes kind = segment target declarative; rule rows only on dynamic segments. Partial unique on active rows (`removed_at is null`). Rows are closed, never deleted → churn history; the FK to `segments` is NO ACTION (a segment with history is archived, not deleted). Written only by functions (`add/remove_segment_members`, `sync_segment_members`, merges); org_admin has select only. |
| `segment_templates` | name, description, target, conditions, category, is_system | System templates read-only. |
| `segment_daily_stats` | segment_id, day, member_count, added, removed | **ro**, trend & churn (SA_3); FK NO ACTION. A close and open of one subject at the same instant (pin) counts as neither added nor removed. |

Conditions: groups `{op:'and'|'or'|'not', children}` (exact keys; `not` has one child; at most 100 children, depth 7); leaves `{field, operator, value}`. The field catalog is the SQL function `itap.segment_field_catalog(target, org)` (tracked query `segment_fields`), the single source for validation, the translator and the UI. Operators per type: text (eq, neq, in, nin, contains), enum (eq, neq, in, nin), integer (eq, neq, in, nin, gt, gte, lt, lte, between), number (no in/nin), boolean (eq), date (eq, neq, gt..lt, between), timestamp (gt..lt, between), references (eq, neq, in, nin); nullable fields add `is_null`. At most 500 values in `in/nin`. jsonb paths (`attributes.*`, `custom_fields.<key>`) support eq/neq/in/nin/is_null only. Dates/timestamps accept an absolute value or `{"relative_days": n}` (|n| <= 36500), resolved at evaluation time. Errors: `segment_condition_invalid:<json path>`.
- **profiles**: profile columns, `custom_fields.<key>`, company, work schedule (`on_shift_now`), `visit_status_today`, `has_face`, `is_blacklisted`, membership in **manual** segments (`member_of_segment`), behavioral (`visits_last_30d`, `avg_dwell_minutes`, `last_seen_days_ago`, `after_hours_visits_30d`, `top_area_id` = most entered area in 30 days) from `profile_activity_stats`.
- **identities**: status, `age` (stored generated column from `attributes.age`), `attributes.gender`, first_seen_at, detection_count, `linked`, membership in **manual** segments, the same behavioral metrics from `identity_activity_stats` (works for unknown identities).
- Referencing only manual segments (with immutable kind/target and undeletable referenced segments) rules out evaluation cycles. References to areas/companies/schedules/segments must belong to the organization (checked at save).
- **Null semantics are two-valued**: a comparison on a missing value (no stats row, null column) is false and `not` is a plain negation, so `not(visits_last_30d >= 2)` matches never-seen subjects; `is_null` is the explicit test.
- Membership writers: `add/remove_segment_members` (manual; adding a current rule member pins it: rule row closed, manual row opened at the same instant), `sync_segment_members(segment, ids, at)` (dynamic; backend only). Lock order: subjects `FOR KEY SHARE` in id order → segment `FOR UPDATE` → member rows. Merges fold open manual memberships onto the target via the merge move log (pin if the target is a rule member); rollback restores exactly.
- Evaluation: one evaluator (backend translator → Hasura `where` under an org session); membership is "as of" a timestamp `at` (`last_evaluated_at` ordering makes older syncs stale). A segment outside its active window/schedule or not `active` closes its rule rows. Failures are recorded on the segment (`last_evaluation_error`).

Pipeline (stream-server snapshot → backend → InsightFace) stays. Changes:

## 8. Server-side logic

### 8.0 Placement and safety rules
- **SQL trigger / SQL function**: anything that must be transactional or idempotent — counters, paths, audit, validation, the per-detection tracking state, event evaluation, event → notification matching, merges/splits. All time logic uses the row's own timestamp (`detected_at`, `occurred_at`), never `now()`, so replaying history (seed) runs the same logic.
- **One evaluator per rule language**: segment conditions are translated to Hasura `where` in the backend only (preview = Action `preview_segment` using the same translator, so Hasura permissions apply); there is no second SQL evaluator.
- **Tracked SQL functions**: every function takes `hasura_session` (session argument) and filters by `x-hasura-organization-id` inside; results returned as rows of tables in `itap_results` that carry `organization_id` with the standard permission filter (double guard). `HASURA_GRAPHQL_INFER_FUNCTION_PERMISSIONS=false`; permissions granted explicitly. Volatile functions are mutations.
- **Actions → backend** only where something outside Postgres is needed (InsightFace, JWT signing, file rendering, storage, external delivery). Handlers call Hasura with the admin secret **and the caller's `x-hasura-role`, `x-hasura-organization-id`, `x-hasura-user-id`** (from the action payload), so Hasura permissions and composite FKs apply and audit records the actor. File arguments are checked against the org bucket.
- **Event triggers → backend** only for external side effects (sending, rendering, syncing). They are at-least-once and concurrent: handlers are idempotent (state checks, unique keys, `ON CONFLICT`), retry config set explicitly.
- **Cron triggers → backend**, which then calls SQL functions per organization.

**Face authentication engine (slice 9, as built).** All admin-only, called by the backend service and the seed. `itap.auth_population(org, app, access_point, at)` / `auth_population_scope` (single evaluator `auth_population_eval`): matchable identities (centroid, not merged/archived, matching enabled, linked to an ACTIVE profile; sandbox: synthetic) in bound non-archived segments or bound facilities (allow policy / grant covering the facility, or a tracking session there in 30 days), then work schedule (`profile_rostered_at`), then the access point (`evaluate_access(..., p_record => false)` granted). `auth_threshold_floor(n)` (<=100 0.50, <=1000 0.55, <=10000 0.60, else 0.65), `auth_effective_threshold` (raise-only request, capped at `threshold_max`, floor wins; verification floor 0.55). `auth_attributes(app, identity, at)` returns exactly the permitted keys. `auth_decide(org, app, session, mode, claimed, access_point, embedding, quality, attack, request_threshold, at, record, evidence_file)`: strict session binding, attack and digest replay (an attack beats a quality failure and closes the session), quality, `liveness_failed` when the application requires liveness and it was `not_checked`, two-stage match (top-20 centroids, then best template), partial band `[t-0.08, t)`; records attempt, digest, session step and `auth_success`/`auth_failed` (dedup `auth:<attempt>`, none for sandbox apps). A verification failure returns identical fields outside the population and below threshold (recorded `not_in_population` vs `below_threshold`; nothing is compared outside the population, no score stored). `review_authentication_attempt(attempt, approve, note)` (org_admin) approves/rejects a pending partial match, closes the session and emits the event. Service entry points: `auth_open_session` (`access_point_required` for apps bound to access points), `auth_service_decide` (decides at DB `now()`), `auth_second_factor` (verification sessions only), `auth_session_state`, `expire_auth_sessions`; `store_client_key` / `revoke_client_key`. Seed only: `itap.seed_auth_flow(session, flow)` with the transaction-local clock `itap.auth_now()` (= `now()` unless `itap.seed_auth_at` is set; live code never sets it).

**Access engine (as built).** `itap.evaluate_access(org, access_point, identity, profile, device, at, record, override_version, detection, finish, session)` (admin-only) is the only evaluator; it returns `itap.access_evaluation` (result, reason, policy_version_id, grant_id, risk_score, signals, decision_id, override_id). `check_access` (org_admin, active member, a presented device must be bound to the access point else `invalid_device`) records at `now()` only and is not a dry run: recording consumes a single-use grant (what-if questions go through `simulate_access_policy`, which writes nothing); Stage B, the seed and simulation call `evaluate_access` directly. Order of evaluation:
1. Person: identity -> effective identity (merge chain) -> linked profile; a profile can be given directly; an identity linked to a different profile raises `identity_profile_mismatch`.
2. Overrides active at `at` covering the access point (area rows = subtrees, none = facility). Order: an **evacuation at an exit** (direction out/both) first (life safety: it opens exits even under `lock_all`), then `lock_all`, `unlock_all`, other evacuations (an evacuation at an entry falls through; entry stays locked under lock_all). Results `override_evacuation` / `override_lock` / `override_unlock`; the trace lists every covering override with `applied`.
3. Access point status inactive/maintenance -> `access_point_unavailable` (after overrides, so an unlock still opens it).
4. No identity and no profile -> `unknown_person`; profile not active -> `profile_inactive` (after overrides, so unlock/evacuation still open for them).
5. Enforced versions (plus the substituted or added `override_version` when simulating): subject (profile, segment membership open at `at`, profile_type, access_level rank ≥; identity-target segments match through the presented identity and every identity linked to the profile), target (access point, area subtree, facility), `valid_from <= at < valid_until`, schedule in the **facility timezone**. Priority desc, deny before allow, then version id; the first match decides; an allow above `max_risk` -> `risk_exceeded`. DST: wall-clock windows (spring-forward: a 02:00-04:00 window is one real hour; fall-back: the repeated hour matches twice).
6. Grants (only when no version decided): not revoked at `at`, in window, for the access point or an area in its path; reusable before single-use. A single-use grant is consumed only when recording, by `UPDATE ... WHERE used_at IS NULL AND (revoked_at IS NULL OR revoked_at > at) RETURNING` under the row lock (one consumer; a concurrent revoke wins).
7. Default: `outside_schedule` (an allow failed only on its schedule), `unknown_person` (no profile), else `no_rule`.
Risk (0..1, clamped): over capacity 0.3; denied decisions of the person in the last 10 min 0.15 each (max 0.45); device health warning 0.15 / critical 0.3 / unknown 0.1 (given device, else the access point's terminal); no profile 0.4. The occupancy and device-health components are read as they are now, also for a past `at` (seed replay, simulation): the risk of a past decision is approximate (deferred minor). An unbound device is ignored (`signals.ignored_device_id`). Recording: decision row (epoch read first without locks, `latency_ms`, `decided_at = at`, `detection_id`), then `access_granted` (info) / `access_denied` (low) through `emit_event` (key `decision:<id>`) and `finish_events` (skipped when `finish => false`; callers that write more events pass false). `signals` is the trace (person, access point, overrides, candidates with subject/target kind, valid, schedule always/in/out, matched, decided, simulated; grants with `applied`/`consumed`; risk components; epoch; `decided_by`). The function runs with `plan_cache_mode = force_generic_plan` (stable ~1.3 ms p95 instead of custom-plan flapping). Matching is shared with Stage B in plain-SQL helpers (`access_person_identities`, `access_subject_match`, `access_target_match`, `access_candidates`, `area_access_allowed`).

**Simulation and analytics.** `simulate_access_policy(version, from, to, limit)` is STABLE and writes nothing (no xid assigned). It takes the decisions in `[from, to)` that still have an access point (≤ 31 days; ≤ 2500 evaluated, an evenly spaced sample beyond, `sampled`), and evaluates each twice at its `decided_at`: baseline (enforced versions only) and candidate (version substituted or added). Transitions are counted baseline -> candidate (unchanged, granted_to_denied, denied_to_granted, reason_changed, skipped when the engine refuses the inputs); `drifted` counts decisions whose baseline differs from the recorded result (policy changed since), and samples carry `recorded_result`/`recorded_reason`/`drift`. Limits: risk uses the current area occupancy and person attributes are current; membership, grants, overrides, schedules and recent denials are evaluated at `decided_at`. `policy_analytics(from, to)` (≤ 366 days) returns one row: totals; hits/granted/denied/last hit per enforced or deciding version; unused enforced versions; denial reasons; top 10 denied (profile, access point); `overlap_hints` (enforced versions with identical subject and target sets: `same_effect`/`conflicting`); grant buckets exclusive as of `p_to` (used > revoked before `p_to` > expired > unused, summing to the total); complexity.

**Policy epoch and terminal distribution.** `itap.bump_policy_epoch(org, urgent)` increments `policy_epoch`; an urgent bump also sets `policy_urgent_epoch`/`policy_urgent_at` and appends `policy_urgent_epochs`. Urgent (access narrows): publish of a deny version or replacing an allow version (and allow with `max_risk`); archive of an allow policy; grant revoke or delete; every override start and end; profile leaving `active`, profile delete, blacklist entry added (unconditional; conservative: neither the engine nor the payload reads blacklists directly, the bump only re-syncs terminals); a linked identity unlinked, relinked to another profile or deleted (merge rollback included); an area path change (area move); segment membership closed (or an open row deleted; deleting closed rows is retention, no bump), profile_type change or lowered access_level only when an enforced version has such a subject (deferred constraint triggers, commit time, once per transaction and organization). Lazy: grant insert; access point status/direction/area change; membership opened or reopened (merge rollback) in a segment that is an enforced subject; a new identity link; profile reactivation; raised access_level when an enforced version has an access_level subject. Grant consumption and expiry do not bump (single-use grants are checked centrally only; terminals enforce `valid_until` and override `ends_at` themselves). `terminal_policy_payload(device)` is the stub terminals' view: covering enforced versions, open members of segment subjects, a `profiles` section (status, type, level, effective identity ids, only profiles that can match a subject or hold an included grant; non-active ones keep their status and lose their grants), active reusable grants with validity, active overrides, timezone, epochs, `generated_at`, sha256 checksum (without `generated_at`); single-use grants are never included. `terminal_sync_status()` reports lag, `urgent_pending`, `seconds_since_urgent` and `within_bound` (synced to the urgent epoch, or the earliest unapplied urgent epoch is at most `policy_revocation_bound_seconds` old; a never-synced terminal is measured from its binding). Terminals are `access_terminal` devices bound with role `terminal`; reachable = status active and health not critical.

**Compliance (slice 10, as built).** Retention: per class `itap.purge_<class>(org, cutoff, facility, subject_profile, subject_identity, limit, action) -> (affected, skipped_by_hold, files_enqueued)` (admin-only, one batch; `purge_class` dispatches) over `retention_candidates_<class>(retention_scope)` (the single definition of a class; the scope snapshots legal holds once per call and applies facility precedence or a DSR subject); guards are bypassed only under the transaction-local `itap.retention_context`; files are queued with `enqueue_unused_files` (checked against `file_in_use`) and deleted by the backend (`claim_file_deletions`). ### 8.2 Detection pipeline
**Stage A — tracking state (SQL, AFTER INSERT on `detections`, same transaction, small and bounded):**
1. Identity `last_seen_at`/`detection_count` (throttled).
2. Session: if the identity's active session in this facility has `last_detected_at` older than the tracking timeout → close it (`completed` if the last location was an `is_entry_exit` access point, else `lost`) and open a new one; otherwise extend. Link a checked-in or scheduled visit of that day.
3. On area change: write `identity_locations` (`unique(detection_id)`) and move `area_occupancy` (`unique(facility_id, identity_id)`); record the transition on the session (`state_changed` marker used by stage B).

**Stage B — event evaluation (Hasura event trigger on `detections` → backend → SQL function `evaluate_detection(detection_id)`, after commit, idempotent):**
Events are emitted on **state changes only**, with dedup keys on the state:
- session opened → `detection_known` / `detection_unknown`, `watchlist_match` / `blacklist_match` / `vip_arrival` (watch list kinds), `inactive_profile_detected` (suspended/terminated profile), `unexpected_facility` (first visit of a known profile), `after_hours` (outside facility operating hours, via `in_windows`; suppressed for an active profile whose work schedule overlaps the detection time ± 30 min, so a rostered night shift is not after hours) — key `(session, type)`;
- area entered → `restricted_area_entry` (per-area governance: an area is *governed* when an enforced **allow** version of any subject covers it (facility, area subtree, an access point leading into it) or a grant of the person covers it; a deny alone never governs. `itap.area_access_allowed`: the first fully matching version decides (priority desc, deny first) in governed and ungoverned areas alike, then a valid grant; otherwise false when governed, NULL when not. Governed and not allowed -> event with payload `basis: 'policy'`; ungoverned areas keep the access-rank comparison with `basis: 'rank'`. Overrides and risk are ignored here — visitors outside authorized areas, FS §9.1), `abnormal_movement` (transition seen at most `abnormal_movement_max_count` times (default 1) in `area_transitions_daily` over the 30 local days before the detection's day, today excluded, while the source area has ≥ `abnormal_movement_min_total` (default 20) departures and the target ≥ that many arrivals; org settings; medium severity), `occupancy_exceeded` (area count passes capacity) — key `(session, type, area)`;
- access point passed (any detection at a door, not only state changes) → **face credential**: for a door with `access_points.face_credential` the bound camera is a reader. `itap.evaluate_face_credential` runs first under the door lock (`pg_advisory_xact_lock('access_point:'||id)`): stop if a decision for this `detection_id` exists (redelivery); stop if the same person (linked profile, else effective identity) has a decision at this door within ± `face_credential_cooldown_seconds` of the detection (terminal decisions count; symmetric, so out-of-order evaluation cannot add a second one); otherwise `evaluate_access(..., record, detection, finish => false)`. Its `access_granted`/`access_denied` event carries `detection_id` and `session_id` and joins Stage B's single `finish_events`. The unique index on `detection_id` is the backstop.
- → `tailgating`: within ± `tailgating_window_seconds` of the detection, **granted ≥ 1 and people > granted** (granted = `granted` decisions at the door; people = distinct persons with decisions at face-credential doors, otherwise distinct effective identities detected by the door's cameras, counted only when the door has at least one decision in the range). Two denied faces are not tailgating (denials already raise `access_denied`). Taken under the door lock; skipped when a `tailgating` event at the door already lies within ± window (one case, one event across bucket boundaries); key `(access_point, type, time bucket)`, severity high.
Published event-rule versions in scope then set severity, `rule_version_id`, and create incidents (`creates_incident`) with the version's escalation policy.

Time-based rules (`loitering`, `unusual_dwell`) are evaluated by cron (§8.3) from `area_occupancy` durations, key `(occupancy row, type)`.

**Stage C — notification fan-out (SQL `itap.fan_out_events`, called by `finish_events` after incident creation and the rule counters; also by `emit_device_event`)**: match active notification rules (event-type and channel junctions, conditions, priority rank) and subscriptions (min severity rank) of active members → `notification_deliveries` + `user_notifications` (in-app delivered immediately); webhook subscriptions → `webhook_deliveries` (pending); a matching rule's `escalation_policy_id` goes onto the event's open incident if it has none. Per-origin partial unique indexes make it idempotent. This runs inside the event writer's transaction (stage B or a cron), at the end of its lock order (event keys → incident counter → rule rows → deliveries), not in the detection insert.

| `end_emergency_overrides` | 1 min (tolerance 120 s) | two-phase: lock every override with `ends_at <= least(at, now())` (`FOR UPDATE ORDER BY id`), emit all `emergency_override_ended` events, one `finish_events`, then update the rows last (`ended_at = ends_at`, `ended_by` NULL, `end_reason = 'expired'`; idempotent; `organization_settings` epoch bump last in the lock order). Evaluation already ignores an override after `ends_at`; the cron closes the record |
| `sync_terminal_policies` | 1 min (tolerance 120 s) | terminals due for sync (`terminals_due_for_sync`): **urgent** = synced epoch NULL or below `policy_urgent_epoch`; **lazy** = below `policy_epoch` and last sync older than 15 min. Backend fetches `terminal_policy_payload`, stub transport delivers iff the terminal is reachable, `record_terminal_sync` (a `synced` result needs a checksum and an epoch not above the organization's `policy_epoch`: `terminal_sync_checksum_required` / `terminal_sync_epoch_invalid`) writes `policy_version_synced = greatest(old, epoch)` / `policy_synced_at` / `policy_sync_error` and a `terminal_policy_syncs` row (failures only on state change). The cron is the safety net; urgent pushes normally happen within seconds through the `policy_urgent_epoch_bumped` event trigger |
| `aggregate_stats` | hourly at :05 | per organization, at the scheduled time: hourly/daily/transition stats over a trailing window `[hour_floor(at − tracking timeout − 180 s) − 1 h, hour_floor(at))` (heals late closes and missed runs; idempotent). Activity stats and segment daily stats are refreshed by `evaluate_segments`; identity confidence refinement is not built |
| `evaluate_segments` | hourly | `run_activity_stats` → all dynamic segments (active, or with open rule rows; time windows, schedules) via the backend translator + `sync_segment_members` → `refresh_segment_daily_stats`; per-segment failures recorded on the segment. Also picks up time-based inputs (watch-list entry expiry) |
| `evaluate_segments_pending` | 1 min | organizations with a `segment_evaluation_requests` row whose first unprocessed request is ≥ 30 s old → evaluate their dynamic segments at `max(scheduled, now())`; stays pending after a stale sync or transient failure |

| `run_saved_searches` | hourly | due saved searches run as their owner (inactive owner → skipped); alerts only for identities new since the previous completed run; the first run or a run after a definition change records the baseline only |
| `resume_bulk_jobs` | 1 min | queued jobs and jobs with an expired lease → resume (skipping rows already applied) |

| `run_integration_schedules` | 15 min (tolerance 1800 s) | integrations with `config.schedule_cron` due (`next_sync_at`) → `schedule` sync runs; stalled runs reclaimed |

| `retention_cleanup` | daily 03:30 UTC (tolerance 3600 s) | per organization `run_retention(org, scheduled_at)` repeated while running (≤ 12 calls of ≤ 20 s): targets in class order, facility-specific first, skipping legal-hold coverage; then the file-deletion drain (storage API) |
| `drain_file_deletions` | 10 min | up to 500 queued file deletions through the storage API (`claim_file_deletions`; 404 = done; backoff, 10 attempts) |
| `dsr_maintenance` | 10 min (tolerance 1200 s) | `due_dsrs` (received requests never claimed, expired leases) → fulfil; then `dsr_overdue_events` (one `dsr_overdue` event per open request past `due_at`) |
| `find_duplicates` | daily | identity template similarity → identity candidates; name/email/employee_id → profile candidates |
| `send_digests` | hourly | digest-mode rules |

| `retry_webhooks` | 1 min | webhook deliveries whose `next_attempt_at` passed (backoff or lease) → claim and POST; `dead_letter` after 5 attempts |

### 8.4 Event triggers (external side effects only)
Segment input changes are not an event trigger: deferred constraint triggers (commit time, once per transaction and organization) on profiles, identities (insert/delete; status/profile_id/attributes), watch_list_entries, watch_lists.kind, visits, work_schedules, manual segment_members and segment definitions write `segment_evaluation_requests` (`requested_at`, `first_requested_at`); the cron `evaluate_segments_pending` consumes them (debounce = batching window, so continuous writers cannot starve evaluation).

| Trigger | On | Does |
|---|---|---|
| `send_delivery` | insert `notification_deliveries` (non in-app) | email → log/Mailhog if configured; sms/push/webhook → stub `sent/delivered`; failures → retries → `dead_letter` |
| `send_webhook` | insert `webhook_deliveries` | real HTTP POST with HMAC-SHA256 signature, retries |
| `render_report` | insert + status update `reports` | acts on `queued` rows: claim (lease, attempt) → `compute_report` → render (CSV/JSON/PDF/XLSX, in-house writers) → upload (`kind = report`) → `complete_report` (event `report_generated`, schedule deliveries, Stage C); failure → `fail_report` and file cleanup. Updates to other statuses are no-ops (Hasura cannot filter by value) |
| `policy_urgent_epoch_bumped` | update `organization_settings.policy_urgent_epoch` | pushes that organization's due, reachable terminals at once (one due query when none), so a revocation meets the 60 s bound (a 1-minute cron alone would not); the cron remains the safety net |
| `run_export` | insert `export_jobs` (payload ids only) | claim (lease, 3 attempts) → query Hasura with a signed org token of the requester (permissions and readable columns apply; keyset pages, `max_rows`) → CSV/JSON/XLSX → upload (kind `export`, owner-only, sensitive) → `complete_export_job` (audit `export`, cursor, `subject_ids`); failure → `fail_export_job`, file cleanup |
| `run_bulk_job` | insert + status update `bulk_jobs` | answers at once and runs the job detached (lease; resume by cron): CSV row by row (limits 10 000 rows / 5 MB), each profile row applied as the job owner by `bulk_apply_profile_row` (same transaction as its `bulk_job_rows` row, dry run rolled back), `bulk_search` rows through the shared search service; progress, cancel, result CSV; `partial` when some rows failed |
| `run_sync` | insert `integration_sync_runs` (payload `id, organization_id, integration_id, trigger`; never the secret) | claim (lease) → HR applies a fixture file (creates / updates changed columns / deactivates absent profiles keyed by `source_integration_id/external_id`, as an org-scoped admin session with audit reason `integration:<code>`; skips restricted and suppressed (erased) people); SIEM/webhook count events, BMS counts occupancy rows (stubs); failure → integration `error`, `last_error`, one `integration_failed` event |
| `fulfil_dsr` | insert `data_subject_requests`, update of `attempts_at_retry` (requeue) | claim (lease, 5 attempts) → access/portability: bundle zip (kind `dsr_export`); erasure: `dsr_erase_restrict` then `dsr_erase`, then the file drain; restriction: `dsr_restrict`; rectification: waits for org_admin (`complete_dsr`); failure → `fail_dsr` (backoff) |

## 12. Designer's calls (not discussed with the owner)
- One `segment_members` table (closed, not deleted) instead of two membership tables.
- Investigation = incident status; events ↔ incidents only via junction.
- `companies`, `visits`, `work_schedules` for the office-center scenario.
- Blacklist and VIP as watch list kinds; profile type list without `blacklisted` (shown via computed `is_blacklisted`); profile `pending` replaced by computed `has_face`.
- Geofences modeled as areas with shapes (incl. `virtual_zone`), no separate table.
- Composite FKs for tenant/user/facility isolation instead of a consistency trigger.
- Detection pipeline split: tracking state in the insert transaction, event evaluation and notifications in SQL right after commit (event trigger → `evaluate_detection`); events only on state changes.
- One versioning pattern (header + versions owning children) for access policies and event rules.
- Two-token flow kept (owner decision) over Nhost custom claims; cost: the client manages the org token and its renewal itself (Nhost SDK only refreshes the base token).
- Merges keep source identities (`merged`) for exact rollback.
- Exact vector scan instead of HNSW.
- Org token TTL 15 min; no platform super-admin; logos in a shared bucket.
- No PostGIS; floor-plan pixel coordinates.
- Seed organization names and volumes.
