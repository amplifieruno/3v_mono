# Data Layer Slice 9 — Face Authentication Service (SA_6) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A face authentication service third-party applications call with key auth: identification against a server-scoped population and verification of a claimed identity, partial-match flow (recapture / second factor / manual review), quality-derived failure reasons, sequence-based attack resistance with session binding, two-stage retrieval with separate instrumentation, population-adaptive thresholds, client application registration (keys, rotation, bindings, permitted attributes), sandbox on synthetic identities, and an evidentiary attempt record — with 30 days of attempts produced by the same decision engine.

**Architecture:** Builds on slices 1–8 (summaries; `.claude/rules/hasura-conventions.md`). Data and decisions in SQL (population, retrieval, comparison, threshold, outcome) so every attempt is reproducible from its record; image work (quality, liveness heuristics, embedding) in the backend via InsightFace. Public REST under `/v1/auth/*` on the backend (key auth, not Hasura JWT), plus Hasura actions for the admin console (test authentication, key rotation). Out of scope here (later deliverables, not data layer): Python/Node client libraries, mobile capture kits — this slice ships the machine-readable interface (OpenAPI 3.1 JSON) they will be generated from.

**Tech Stack:** Postgres 16 + pgvector (exact scan), Hasura v2.46, Express/TypeScript, InsightFace-REST, Node `crypto` (HMAC-SHA256, scrypt for key hashes), vitest.

**Spec:** `tasks/data-layer/design.md` — §6.16, §6.3 (identities.is_synthetic), §7, §8.1 (`sandbox_population_check`), §8.5 (`authenticate_face`, `rotate_client_key`), §9; `docs/stages/SA_6_EN.md` §2.1.1–2.1.3, §2.1.6–2.1.7, §3.

## Global Constraints

- All conventions apply. `authentication_attempts` **ro**, append-only, not audited (high volume), searchable by application, identity, session, outcome, period (indexes). Access to attempt rows with images is logged (`view_sensitive` audit via `open_file`, as for reports).
- Sessions: `authentication_sessions` (application, device_ref, nonce (random 32 bytes, stored hashed), mode, claimed_identity_id, status `open/succeeded/failed/review/expired`, step count, expires_at (5 min), created_ip) — every authentication runs under a session; steps: initial → recapture (≤2) → second_factor → review.
- Keys: `client_application_keys` prefix (public, 8 chars) + secret hash (scrypt); plaintext returned once by `rotate_client_key`; requests authenticated by `Authorization: ITAP-HMAC key=<prefix>, ts=<unix>, sig=<hex>` over `method\npath\nts\nsha256(body)` with ±300 s skew; revoked/expired keys and non-active applications refused.
- Population (server-side only, never from the request): identities linked to profiles in the app's bound segments (open membership) ∪ facilities (profiles with sessions/assignments there — define: profiles whose work schedule or company is bound? → use: identities seen in the facility within 30 days or profiles with active grants/policies there; document) ∩ optional access point narrowing (identities allowed by `area_access_allowed`/policies for that access point at `now`) ∩ `use_work_schedules` (profiles on shift ±30 min, reusing `profile_rostered_at`); sandbox apps: only `is_synthetic` identities; production apps never see synthetic identities.
- Threshold: similarity threshold = max(app threshold, floor(population_size)) clamped to [threshold_min, threshold_max]; floor function `itap.auth_threshold_floor(n)` (documented table: n ≤ 100 → 0.50, ≤ 1 000 → 0.55, ≤ 10 000 → 0.60, larger → 0.65); verification floor fixed 0.55 independent of population; request threshold may only raise, never lower below the floor. Partial match band: [threshold − 0.08, threshold).
- Two-stage retrieval: stage 1 top-K (K = 20) identities by distance to a per-identity centroid (`identity_centroids`, maintained by trigger on embeddings); stage 2 exact comparison over all templates of the retrieved candidates; record retrieval_candidates, retrieval_hit (claimed/true identity within top-K when known), comparison_score, population_size, population_scope snapshot.
- Attack resistance (cheap, real): sequence of 3–5 frames required; per-frame quality via existing face quality checks (no_face/multiple_faces/low_quality/blur/poor_lighting reasons); injection/replay: sequence digest (sha256 of frames) seen before → `injection`; identical frames (no inter-frame change) → `screen_replay`/`printed_photo` heuristic (document thresholds); session binding: request must carry HMAC over (session nonce ‖ sequence digest ‖ device_ref) with the app key, else `injection`; masks → `not_checked`. Attack outcome recorded separately from match outcome.
- Evidence: keep one frame (crop) for partial/failure/attack outcomes in the org bucket (kind `auth_evidence`, owner-only? → org-readable for admins, audited on open); discard all frames for successes; record model_version (InsightFace model name) and threshold_used.
- Events: `auth_success` / `auth_failed` via emit_event (dedup `auth:<attempt id>`), Stage C fans out.

## Review Focus

1. A client application cannot widen or narrow its own population or lower the threshold below the population floor through any request field.
2. Verification of an identity outside the app's population returns the same failure as a non-match (no oracle), and is recorded.
3. A replayed sequence (same digest) or a sequence bound to another session/app is refused as an attack and recorded as such, distinct from no-match.
4. A sandbox application never retrieves or receives a production identity, and production apps never see synthetic ones.
5. The attributes returned are exactly the app's permitted set; never the identity record.

### Task 1: Schema — client applications, bindings, keys, sessions, attempts, centroids, synthetic guards
Enums (platforms, statuses, modes `identification/verification`, attribute set `display_name/photo/profile_type/company/department/employee_id/access_level/segments`, steps, outcomes, review statuses, failure reasons, attack outcomes); tables per spec §6.16 + `authentication_sessions`, `identity_centroids` (identity_id pk, centroid vector, template_count, updated_at; trigger on identity_embeddings insert/delete; merged identities' centroids removed), `auth_sequence_digests` (digest unique per org, first_seen_at, attempt_id) ; `sandbox_population_check` triggers (sandbox apps bind only segments whose members are synthetic? → enforce at evaluation time + app-level: sandbox apps may not bind facilities/access points); `rotate_client_key` SQL (returns plaintext once — generate in backend action and store hash; SQL stores hash) ; review functions `review_authentication_attempt(hasura_session, attempt, approve bool, note)`; permissions (org_admin CRUD apps/bindings; keys select metadata only; attempts select; sessions select); indexes for search. Tests.

### Task 2: Decision engine in SQL
`itap.auth_population(app, access_point, at)` (set of identity ids + scope jsonb), `itap.auth_threshold_floor(n)`, `itap.auth_decide(app, session, mode, claimed_identity, access_point, embedding vector, quality jsonb, attack jsonb, at, p_record bool)` → outcome, matched identity, confidence, threshold_used, retrieval stats, failure_reason, attempt id; writes attempt + session step + event when p_record; identification two-stage; verification single comparison (claimed outside population → failure not_in_population recorded, response identical to below_threshold); permitted attributes projection `itap.auth_attributes(app, identity)`. Tests: Review Focus 1, 2, 4, 5; threshold table; partial band; retrieval_hit instrumentation.

### Task 3: Backend service + REST + actions
`apps/backend/src/auth-service/`: key auth middleware (HMAC, skew, key lookup by prefix, constant-time compare), `POST /v1/auth/sessions` (nonce returned once), `POST /v1/auth/authenticate` (sequence 3–5 frames base64 ≤ 5 MB total, binding HMAC, mode, claimed identity, access point, threshold (raise-only), timeout (≤ 10 s)), `POST /v1/auth/sessions/:id/recapture`, `POST /v1/auth/sessions/:id/second-factor` (app asserts factor result; recorded), `GET /v1/auth/health` (InsightFace + DB; degraded → 503 retryable code), structured errors per FS (code, message, retryable, guidance); quality + liveness heuristics + digest replay; evidence retention; actions `authenticate_face` (admin console test using a stored file id and an app) and `rotate_client_key`; OpenAPI 3.1 JSON at `GET /v1/auth/openapi.json` (generated from zod schemas or hand-written + validated in tests). Tests: Review Focus 3; end-to-end with real seeded faces; latency at the boundary measured.

### Task 4: Seed
Client apps: "Lobby Kiosk" (identification, turnstile access points, Employees segment, work schedules on, attributes display_name/company/photo), "HR Portal" (verification, all employees, attributes display_name/employee_id/department), "Visitor Check-in" (identification, visitors segment, reception access point), "Developer Sandbox" (is_sandbox, synthetic identities — generate ~20 synthetic identities with generated faces + embeddings), one suspended app; keys (one rotated, one revoked); 30 days of attempts produced by `auth_decide` with probes derived from stored templates + noise (no InsightFace calls for history), all outcomes incl. partial→recapture→success flows, attacks (replay/injection/printed), reviews pending/approved/rejected; evidence files for a few failures. Seed test invariants; time budget ≲ +30 s.
