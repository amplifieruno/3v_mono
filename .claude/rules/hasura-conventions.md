# Hasura and Database Conventions

## Data Access

- All data access goes through Hasura GraphQL. Never query PostgreSQL directly from application code.
- Use Hasura's generated GraphQL API as the single source of truth for CRUD operations.
- For complex business logic that cannot be expressed as Hasura actions, use custom Express handlers that are called via Hasura Actions or Events.

## Schema Management

- Schema changes are SQL migrations in `apps/nhost/nhost/migrations/default/`; apply with `make hasura_apply` (reset the dev DB with `make db_reset`).
- Metadata for tables in the `itap` schema is GENERATED by `pnpm --filter nhost metadata:generate` from the table definitions in `apps/nhost/metadata-src/`. Never hand-edit the generated `itap.*` metadata files; change the generator inputs and regenerate. Metadata for `auth`/`storage` tables and actions may still be edited by hand.
- `INFER_FUNCTION_PERMISSIONS` must stay `false`. Tracked SQL functions take a `hasura_session` argument where they depend on the session, and get explicit permissions.
- Tracked functions are GENERATED too: add a `FunctionSpec` to `functions` in `metadata-src/index.ts` (`exposedAs`, `sessionArgument: 'hasura_session'`, `customName`, `roles`); the generator writes `databases/default/functions/itap_*.yaml` and the `functions.yaml` include list, and checks the function exists, its session argument is `json` (and fails when a function has a `json hasura_session` argument the spec does not declare as `sessionArgument`), volatile functions are mutations, every role can select the return table, a function exposed to any role declares `sessionArgument`, and each role's select filter on the return table restricts `organization_id` (opt out only with `unscopedReturnReason: '<why>'`). Functions that depend on the caller take `hasura_session json` and read `x-hasura-organization-id` / `x-hasura-user-id` from it. A function with `roles: []` is callable only with the admin secret (e.g. `claim_invitation`, used by the `accept_invitation` action). Result row types live in `itap_results` (hide their root fields with `query_root_fields: []`).
- Mutation functions resolve every id inside `x-hasura-organization-id` (foreign ids raise the not-found code, nothing changes) and write explicit audit rows (`merge`, `rollback`, `approve`, `reject`) with the session `x-hasura-user-id`. Identity status `merged` and sources `merge`/`split` are reserved for the merge/rollback/split functions: a trigger rejects them unless the transaction-local flag `itap.merge_context` is `on`; functions that set it reset it before returning.

## Migrations

- Migration file naming: `{timestamp}_{description}` (e.g., `1707000000000_create_identities_table`).
- Each migration must be reversible -- include both `up.sql` and `down.sql`.
- One logical change per migration. Do not bundle unrelated schema changes.
- Test migrations locally before committing.

## Permissions

- Define all row-level and column-level permissions in Hasura metadata.
- Never implement permission checks in application code that duplicate what Hasura handles.
- Use Hasura roles to model access levels. Tenancy roles are `user` (base token: own memberships, `switch_organization`) and `org_admin` (org token, scoped to `x-hasura-organization-id`; its allowed roles are `[org_admin]` only, so it cannot renew itself). `public` (unauthenticated) sees nothing.
- Use session variables (`x-hasura-user-id`, `x-hasura-organization-id`) for permission filters.
- Rows that need someone's consent or a business check (memberships, invitations) get no direct insert permission; an Action creates them.

## Foreign Keys and Tenant Integrity

- Every tenant row carries `organization_id`. An FK between two tables that both have `organization_id` is composite: `(organization_id, x_id) REFERENCES t (organization_id, id)` (the parent needs a matching unique key), so a row can never point into another organization.
- Every FK column set has an index leading with `organization_id` plus the FK columns (a PK or unique key counts). Both rules are enforced by `metadata:generate`, which fails naming the constraint.
- `ON DELETE NO ACTION`, not `RESTRICT`, for references that an organization cascade removes in the same statement: NO ACTION is checked at statement end, RESTRICT fails mid-cascade.
- To null only the non-org column of a composite FK, use `ON DELETE SET NULL (x_id)` (PostgreSQL 15+); never null `organization_id`.
- `auth.users` rows are never deleted (disabled/anonymized), so FKs to them are `NO ACTION`.

## Reusable Triggers

- `updated_at`: `BEFORE UPDATE ... EXECUTE FUNCTION itap.set_updated_at()`; `itap.set_updated_at_except('<col>', ...)` when system counters must not bump it (e.g. `event_rules.trigger_count`).
- Audit: `CREATE TRIGGER audit AFTER INSERT OR UPDATE OR DELETE ... EXECUTE FUNCTION itap.audit_row_change('secret_col', 'ignore:system_col')` (plain args are redacted, `ignore:` columns are skipped). `audit_log.entity` is always the table name.
- File columns: `BEFORE INSERT OR UPDATE ... EXECUTE FUNCTION itap.check_file_bucket('photo_file_id', ...)` (file must be in the row's organization bucket). `organizations.logo_file_id` must be in the shared `org-logos` bucket.
- Assignment/recipient user columns: `BEFORE INSERT OR UPDATE ... EXECUTE FUNCTION itap.active_member_check('assignee_user_id', ...)` (active, unexpired member). Unknown column arguments raise `undefined_column`.
- Commit-time (deferred constraint) triggers fire in trigger name order within one row event; across rows (and statements), queue order applies. A deferred trigger that takes a lock that must come last (the access epoch bumps lock `organization_settings`) is named to sort after the others on the same table: `zz_access_credentials_*` run after `segment_inputs_changed*` (migration `1792365700193`). A new deferred trigger on those tables picks a name that keeps this order.
- Session-member columns (`added_by`, `author_id`, `from_user_id`): `BEFORE INSERT ... EXECUTE FUNCTION itap.stamp_session_member('<col>')` fills a NULL column with the session user when that user is a member of the row's organization; mark the column read-only in metadata. BEFORE triggers fire in name order, so name the stamp trigger so it sorts before an `active_member_check` on the same column.

## Event and Cron Triggers

- Hasura event triggers and cron triggers call the backend router `POST /hasura/events/<trigger name>` (`apps/backend/src/events`, authenticated with `x-action-secret` like actions). Register the handler in `defaultEventHandlers` (`defineEventHandler` / `defineCronHandler`); the registry key IS the trigger name, and the payload's trigger name must match.
- Cron triggers are GENERATED: add a `CronSpec` to `apps/nhost/metadata-src/crons.ts` (`name`, `schedule`, `includeInMetadata`, optional `retry`, `toleranceSeconds`) and run `metadata:generate`; never edit `cron_triggers.yaml` by hand.
- `toleranceSeconds` (default 21600 = 6 h) is how late a missed run is still delivered. Frequent probes set it to about two periods (`device_health_check`: 120) so an outage does not replay hours of stale runs; set it high only for work that must run eventually.
- Handlers are idempotent (Hasura retries deliver the same payload `id`; use `ctx.idempotencyKey` with unique keys / `ON CONFLICT`) and do the real work in SQL functions called per organization; a handler error is a 500 so Hasura retries. A row that vanished (its organization was deleted) is a no-op success, not a retry.
- Hasura's delivery logs (`hdb_catalog.event_log`, `event_invocation_logs`, cron and scheduled events) are purged daily by the cron `purge_trigger_logs` (`itap.purge_trigger_logs(at, keep_days 3)`): finished rows older than 3 days, every trigger. New triggers need nothing; keep their retry span well under 3 days.

## Same-Facility Composite Foreign Keys

- A row that references two entities of one facility (a device and its area, an access point and its device) carries `facility_id` and uses three-column FKs: `(organization_id, facility_id, x_id) REFERENCES t (organization_id, facility_id, id)`. The parent needs `UNIQUE (organization_id, facility_id, id)`. Constraint names `<table>_<ref>_fkey`; the covering index leads `organization_id, facility_id, x_id`. A mismatch of facilities is then impossible at the database level.

## Shape and Window Columns

- jsonb columns are validated by IMMUTABLE CHECK helpers (`itap.valid_shape`, `itap.valid_windows`, `itap.valid_point`) that never raise and return false for NULL, so a nullable column says `CHECK (shape IS NULL OR itap.valid_shape(shape))`.
- `valid_windows`: JSON array (possibly empty) of objects with exactly the keys `days` (non-empty array of integers 1..7, ISO weekday), `from` (`HH:MM`, 00:00..23:59) and `to` (`HH:MM` or `24:00`; `to < from` is an overnight window). Read by `itap.in_windows`.
- `valid_shape` (floor-plan pixel space): `{"type":"Polygon","coordinates":[ring,...]}` (first ring is the outline, the rest are holes; a ring has at least 3 distinct points, a closing point is optional) or `{"type":"Circle","center":[x,y],"radius":r}` with r > 0; exactly these keys.

## Statement-Level Guards for Tree Moves

- Row-level BEFORE triggers cannot see what other rows of the same UPDATE do. For hierarchies (`areas.parent_id`, materialised path) use a statement-level AFTER trigger with transition tables (`REFERENCING OLD TABLE AS old_rows NEW TABLE AS new_rows`) to reject a single statement that re-parents rows to different parents (`area_multi_parent_move`); moving several rows under one parent stays allowed, and Hasura `update_*_many` runs one statement per entry. Subtree path rewrites run in an AFTER trigger at statement end.

## Telemetry Tables

- High-volume telemetry (`device_health_metrics`, `device_events`) has no audit trigger. Its FK to the parent (`devices`) is `NO ACTION` by this slice's own decision (not spec §6.0, which says `SET NULL` for logs that reference devices): a per-device series without its device is meaningless, so a referenced device cannot be deleted; retire it with `status = 'inactive'`. An organization delete still cascades through `organization_id`.

## Detection Pipeline

- Stage A (`itap.track_detection`, AFTER INSERT on `detections`, same transaction) maintains `tracking_sessions`, `identity_locations`, `area_occupancy` and the throttled identity counters. All time logic uses `detected_at`, never `now()`.
- Per-identity serialization: the BEFORE INSERT trigger `detections_derive` takes `pg_advisory_xact_lock(hashtextextended('identity:' || identity_id::text, 0))` before the FK check locks the identity row. Any other writer of an identity's tracking state (e.g. `close_stale_sessions`) must take the same advisory lock first, before it touches (or FK-references) the identity in its transaction. Reason: an UPDATE of a table whose unique key contains a stored generated column (`code`) counts as a key update in PG16 and waits for other transactions' FK `KEY SHARE` locks; a row lock taken after the FK check deadlocks.
- Insert ordering: one detection row per statement, or multi-row inserts sorted by `identity_id` (then `detected_at`); within one identity rows must be in `detected_at` order (Stage A runs in row order; an older row after a newer one is a late detection and changes no tracking state).
- Identity counters: `detection_count` is incremental (a throttled write adds the identity's detections with `detected_at` in (last_seen_at, NEW) plus NEW; a detection at or before `last_seen_at` is added at once). Never recount an identity's history in Stage A.
- Closing a session uses `itap.close_tracking_session(org, session)` (`completed` if the last detection's access point is entry/exit, else `lost`; clears occupancy). The `close_stale_sessions` cutoff is `at - tracking timeout - 60 s` (grace for detections still in flight).
- Stage B (`itap.evaluate_detection(detection)`, admin-only; event trigger `detection_created` -> backend) emits events only on the state changes Stage A recorded (session opened = `opened_by_detection_id`, area entered = the detection's `identity_locations` row). Every event writer builds an `itap.events` row and calls `itap.emit_event(row[, version])` (rules in scope via `itap.matching_rule_versions`, severity, `rule_version_id`, `payload.rule_version_ids`) for all its events, then `itap.finish_events(org, new_event_ids)` once (incidents via `incidents.dedup_key`: one per session and rule, `occupancy:<area>:rule:<rule>:<bucket>` for occupancy_exceeded; then rule counters).
- Lock order of event writers: (1) event dedup keys, in a fixed order (session events, area events, occupancy areas by depth then id), (2) the per-organization incident counter and incident keys, (3) `event_rules` rows in rule id order, (4) Stage C: the event's incident row (only when a notification rule's escalation policy is put on it), delivery / inbox / webhook rows, and last the `notification_rules` rows (`last_triggered_at`, rule id order). Never write an event after an incident in the same transaction: a writer holding the counter while waiting for an event key held by another writer that waits for the counter deadlocks. Dedup keys: `session:<id>:<type>[:<area_id>|:<watch_list_id>]`, `occupancy:<area_id>:occupancy_exceeded:<15-min bucket>`, `occupancy:<occupancy_id>:<type>:<area_id>:<entered_at ms>[:<rule_id>]`, `device:<id>:<type>:<checked_at ms>`, `decision:<id>` (access decisions), `ap:<id>:tailgating:<floor(epoch / window)>`. Stage B prepends (slice 8): the door advisory lock `access_point:<id>` (taken first, at the start of `evaluate_detection`, for every detection with an access point, before anything is written; `evaluate_tailgating` re-takes it re-entrantly and the tailgating key is only written under it) -> the grant row (single-use consumption) -> then the event keys in the order decision, session, area, occupancy, tailgating.
- Crons `close_stale_sessions` / `evaluate_dwell_rules` call `itap.close_stale_sessions(org, at)` / `itap.evaluate_dwell_rules(org, at)` per organization with the scheduled time. Access ranks: `itap.access_rank(level)` maps profile and area access levels onto one 1..4 scale.

- Watch-list matches are evaluated as of the detection time: `itap.identity_watch_lists(org, identity, at)` counts an entry only when `created_at <= at` and it has not expired by then (a seed that back-dates history must back-date its entries).
- Watch-list rules: `parameters.watch_list_kinds` (non-empty array of `watch_list_kinds`) restricts a `watchlist` rule version to the list kinds it names (blacklist_match -> blacklist, vip_arrival -> vip, watchlist_match -> watch); absent = every kind.
- Incidents open at their event: `incidents.created_at` (and its creation activity) is the triggering event's `occurred_at`, not `now()` (late redelivery and the seed replay get the true time). The incident title is `<rule name>: <event title>` unless the event title already starts with the rule name.

- Visits: `visits.status`, `checked_in_at`, `checked_out_at` change only through `check_in_visit` / `check_out_visit` / `cancel_visit` (org_admin) and the daily `lifecycle_jobs` cron (`itap.run_lifecycle_jobs(org, at)`, scheduled time and organization timezone, idempotent). Stage A links a session to a visit only when it opens (checked-in visit first, else scheduled with `detected_at` in `[expected_start - 2h, expected_end]`; a visit facility must be null or equal).

## Notifications (Stage C)

- Stage C (`itap.fan_out_event(s)`) runs inside `finish_events` AFTER incident creation and the rule counters: full lock order event keys -> incident counter -> `event_rules` rows -> the event's incident row (escalation policy from a matching notification rule, only when the open incident has none) -> delivery / inbox / webhook rows -> `notification_rules` rows (`last_triggered_at`, id order). Deliveries take only their own sorted dedup keys, never the counter lock, never write an event. Safe because no writer locks `event_rules` or `notification_rules` after an incident row (escalation and acknowledgement lock only the incident, then write deliveries / inbox rows).
- Delivery state machine (`notification_deliveries`, read-only, guarded by trigger): `pending -> sent -> delivered`, `failed`/`retrying`, terminal `dead_letter` and `digested` (with `digested_into`). Sending is lease-based: the claim keeps `pending`/`retrying`, does `attempts + 1` and sets `deliver_after = now() + 60 s` (original time kept in `content.scheduled_for`); the finish is guarded by the attempt number; after 5 attempts the claim dead-letters (`error = 'max_attempts'`), and a row whose recipient user is no longer an active, unexpired member is dead-lettered by the claim (`error = 'recipient_inactive'`, scheduled time kept); the due function includes expired leases, never-triggered rows and released quiet-hours rows. Senders must tolerate a delivery row that disappeared.
- Webhooks: `finish_webhook_delivery` locks the subscription row, then the delivery row (parent first); body built at fan-out, signed HMAC-SHA256 (`x-itap-signature`) with the write-only subscription secret, 10 s timeout, no redirects, backoff 30 s / 2 min / 10 min / 30 min, 5 attempts. SSRF guard: URL without credentials, DNS check blocks link-local/metadata always and loopback/private unless `WEBHOOK_ALLOW_PRIVATE_TARGETS` (prod false). The dev sink is gated by `WEBHOOK_SINK_ENABLED`.
- Private audit entities: `audit_log` select for org_admin excludes personal entities (`notification_subscriptions`, `operator_workspaces`, `user_notifications`) unless the row's `user_id` is the caller; NULL-actor rows are hidden from everyone. New personal tables join that list.
- `itap.seed_context` (transaction-local, seed only) lets the history finalizer bypass the delivery guards and the inbox now() stamping (created_at, read/ack times stay as set); nothing else may use it.
- Notification rules and escalation steps that produced deliveries are not deleted: deactivate (`is_active`); steps are edited in place. Subscriptions unsubscribe via `is_active`.
- Escalation: at most one step per incident per cron run, shared `itap.escalate_one` for cron and manual escalation, `max_cycles` bounds repeating policies (required when `repeat`). Policy sources: the event rule version (at incident creation) or, when that gave none, the first matching notification rule with a policy (Stage C). `escalation_step` / `last_escalated_at` are not audited (`ignore:`); the `escalated` activity records each step. `acknowledge_notification` of an escalation page (delivery with `escalation_step_id`) acknowledges the open, unacknowledged incident through `acknowledge_incident` (incident row locked first). Escalation steps and notification rules never use the `webhook` channel (CHECK).

## Segments

- Membership rows (`segment_members`) are closed (`removed_at`), never deleted; history FKs are NO ACTION, so a segment with history is archived. `kind` and `target` of a segment are immutable; a dynamic segment must have conditions; only manual segments can be referenced by conditions (no cycles).
- Manual vs rule: manual rows are written only by `add/remove_segment_members` (and merge folding); rule rows only by `sync_segment_members` (backend, roles `[]`) and only on dynamic segments. Sync never touches manual rows; adding a current rule member pins it (close + open at the same instant, which the daily stats count as neither added nor removed).
- Lock order: subjects (`FOR KEY SHARE`, id order) -> segment row `FOR UPDATE` -> member rows; merges lock identities first. Any new writer follows it.
- Evaluation is "as of" a time: `sync_segment_members(..., at)` ignores `at < last_evaluated_at` (stale). Callers use the scheduled time, never future times; consumers (event rule segment scopes, notification `segment_id` condition) check membership at the event's `occurred_at` (`itap.subject_in_segment`), so seeds back-date membership. Scope kinds combine with AND, scopes of one kind with OR.
- Input changes request evaluation through deferred constraint triggers (commit time, once per transaction and org) writing `segment_evaluation_requests`; the cron `evaluate_segments_pending` consumes them after a 30 s batching window. Never use statement-level triggers that lock the per-org request row. Time-based inputs (expiry) are picked up by the hourly cron.
- Conditions use only fields of `itap.segment_field_catalog`; comparisons are two-valued (null compares false, `not` negates); a new field needs a catalog entry, a translator mapping and a coverage test. Evaluation failures are recorded on the segment (`last_evaluation_error`), never swallowed.

## Analytics, Reports, Search, Bulk (slice 7)

- Stats buckets (`area_hourly_stats`, `facility_daily_stats`, `area_transitions_daily`) are derived, **ro**, not audited, FKs to facilities/areas CASCADE. Hourly buckets are UTC hours (area_id NULL = facility total, unique key `NULLS NOT DISTINCT`); daily buckets are facility-local days and always cover the whole day with the data present, so run order never matters. Writers (`aggregate_stats`, `aggregate_stats_range`) upsert only changed rows, delete rows that lost their data and re-aggregate a trailing window; identities count once by effective (merge) identity. No parent-area roll-up (unique counts cannot be summed).
- Work claimed by the backend (reports, bulk jobs) uses a lease/attempt fencing pattern: `claim_*` moves queued (or expired lease) -> running/generating, adds 1 to `attempts`, sets `lease_expires_at`; every later writer takes the attempt and is a no-op for a stale one; `attempts_at_retry` keeps the fencing token monotonic across `retry_*` while the max-attempts check counts `attempts - attempts_at_retry`; an event trigger starts the work, a cron (`due_reports`, `resume_bulk_jobs`) reclaims expired leases; status transitions are enforced by a SQL guard for every writer; a failure deletes any uploaded file (best effort) and calls `fail_*` first.
- Cron-driven schedules (report schedules, saved searches) are guarded by `next_run_at = run_at` under a row lock, use the cron's scheduled time for timestamps, never replay missed runs, isolate failures per schedule (record `last_error`, continue) and throw only when a failure cannot be recorded. Cron expressions are the 5-field subset checked by `itap.valid_cron`.
- Owner-only files: kinds in `itap.owner_only_file_kinds()` (`search`, `bulk_input`, `bulk_search_result`) are visible/openable only by their uploader (`uploaded_by_user_id`, preset on org_admin upload) and `itap.check_file_bucket` refuses them on every other file column. Owner-only tables filter by a direct owner column (`search_requests.user_id`, `bulk_job_rows.private_owner_id`); `search_results` filters through its `search_request` relationship, which is fine because no mutation function returns it (see the next rule). Their audit rows are private audit entities. A secret-like column readable only by the owner uses a computed field with `session_argument` (`owner_last_error`).
- A mutation function's return table must not have a select permission filtering through a relationship: Hasura wraps the function in an `EXISTS` on the parent and Postgres can skip the function when no parent row is visible (silent `[]`). Use a direct filter column (`private_owner_id`).
- `profiles` insert/update permission and `itap.bulk_apply_profile_row` are a sync pair: the function writes the same column set org_admin may write (it runs as the job owner so triggers, audit and CHECKs apply). Changing one requires changing the other.
- CSV: RFC 4180 writer/parser in the backend (CRLF out, BOM tolerated in, no dependency). `formatCsv` guards formula injection by prefixing with `'` text cells starting with `=`, `+`, `@`, tab or CR, or `-` unless the whole text is a plain number (`^-?\d+(\.\d+)?$`). Reports and bulk result files share it. Bulk input cells with a NUL character fail the record (`invalid_value:<column>`); error texts written to the database drop NULs.
- Backend-claimed work retries a row on transient SQLSTATEs (40P01, 40001, 55P03, from `HasuraError.sqlState`) a bounded number of times; SQL row functions raise those as a message code (`bulk_row_transient`, visible without Hasura internal errors) instead of recording a row failure. Search requests left queued / running are closed as `failed` / `interrupted` (at bulk claim, and after 10 minutes by `resume_bulk_jobs`).
- Tests are run with `vitest run` only, never watch mode (`pnpm test` in `apps/backend` watches and re-runs on every change).
- Dashboards: `widgets` follow `itap.valid_dashboard_widgets` (kind, title, a `query` from `itap.dashboard_widget_queries`, free-form `params`, 12-column `position`); the check never raises; every source is permission-checked for the viewer.

## Versioned Entities

- Event rules (and access policies, slice 8) follow spec §6.0: header (`current_version_id` read-only) + versions (`status` -> `version_statuses`: draft / pending_approval / published / superseded; `version` per header) + children with `version_id` (CASCADE). Helpers in migration `*_create_versioning_helpers`: triggers `assign_version_number('<parent col>', '<schema.header>')`, `guard_version_status()` (published/superseded reserved for publishing via the transaction-local flag `itap.version_context`; frozen versions' content never changes), `guard_version_children('version_id', '<schema.versions>')` (children change only while the version is open); functions `itap.create_draft_version(versions, header, parent col, children[], org, parent)` (open draft or a copy of the current version with its children) and `itap.publish_version(versions, header, parent col, org, version, actor)` (supersede previous, publish, flip `current_version_id`; republishing a superseded version = rollback). Tracked wrappers (`create_event_rule_draft`, `publish_event_rule_version`) resolve the session organization and write the `publish` audit row.
- Partial unique indexes: one `published` and one open (`draft`/`pending_approval`) version per header.
- `itap.create_draft_version_from(versions, header, parent col, children[], org, parent, source)` copies a given version (children included) into a new draft; raises `version_open_exists` while a draft / pending version exists.

## Physical Access (slice 8)

- Enforced = the header's `current_version_id` is set and the policy is not archived; `published` == enforced (archive supersedes the enforced version and rejects a pending one back to draft with `policy_archived`). The header pointer changes only inside `publish_version` (`itap.version_context`, to a published version of the same policy) or archive (`itap.access_archive_context`, to NULL); `is_archived` / `archived_*` only under the archive flag (trigger `guard_access_policy_header`, also against admin-secret GraphQL and SQL). A version becomes `published` only under `itap.access_approval_context` (no direct `publish_version` republish, even from SQL).
- Access policies are versioned like event rules, plus approval on the version: `submit_access_policy_version` (draft -> pending_approval, needs >= 1 subject and >= 1 target, `submitted_by` = caller), `approve_access_policy_version` (pending -> published through `publish_version` by a member other than the submitter, else `four_eyes_required`; audit rows `approve` + `publish`), `reject_access_policy_version(version, reason)` (pending -> draft, `rejection_reason`; audit `reject`), `archive_access_policy` (is_archived, clears `current_version_id`; terminal), `create_access_policy_draft(policy[, from_version])`. Status and approval columns change only under the transaction-local flag `itap.access_approval_context` (trigger `guard_access_policy_version`); a pending version and its children are frozen (`access_policy_version_pending`). There is no direct republish: rollback = `create_access_policy_draft(policy, <superseded version>)`, then submit + approve. New versions never carry approval data (cleared on insert).
- Subjects: exactly one of profile / segment / profile_type / access_level (minimum clearance via `itap.access_rank`). Targets: exactly one of facility / area (subtree) / access point. `access_points` has `UNIQUE (organization_id, id)` for cross-facility references.
- Grants (`access_grants`): org_admin inserts and reads only; `granted_by` stamped; `used_at` set once, only on `single_use` grants (by the engine under a row lock); revocation only via `revoke_access_grant` (flag `itap.access_grant_context`); a used grant is never deleted (`access_grant_used`).
- Emergency overrides and their areas are written only under the flag `itap.override_context` (start/end functions, end cron); an update may only end an override once; justification >= 10 characters, `ends_at` within 24 h of the start; no area rows = whole facility.
- `access_decisions` is append-only, ro, not audited; `result` -> `access_decision_results` (granted/denied), `reason` -> `access_decision_reasons` (override_lock, override_unlock, override_evacuation, policy_deny, policy_allow, grant, risk_exceeded, outside_schedule, no_rule, unknown_person, profile_inactive, access_point_unavailable); `signals` is the full trace, `epoch` the policy epoch used. People / devices / places are SET NULL; the deciding version / grant / override are NO ACTION (attribution kept).
- Distribution: `itap.bump_policy_epoch(org, urgent)` increments `organization_settings.policy_epoch` (+ `policy_epoch_at`) and, when urgent, sets `policy_urgent_epoch` / `policy_urgent_at` (not audited, no updated_at bump). Triggers bump on: `access_policies.current_version_id` change (urgent when the new version denies or the replaced one allowed), grant insert (lazy) / revoke or delete (urgent), override start and end (both always urgent, see the urgency table below). ## Face Authentication (slice 9)

- Client applications (`APP-xxxxx`): thresholds are cosine similarities with `threshold_min <= threshold <= threshold_max` in 0..1; `is_sandbox` is fixed at insert (insert-only + trigger `client_application_sandbox_immutable`); `revoked` is terminal. Bindings are junctions (modes, attributes, segments, facilities, access points; targets NO ACTION). `sandbox_population_check`: sandbox apps bind no facilities / access points (`sandbox_location_binding`); synthetic filtering of segment populations happens in the decision engine.
- Keys: `key_prefix` (8 alphanumerics, globally unique) + `secret_hash` (secret column, redacted in audit). Stored only by `store_client_key` (admin-only, called by the backend action with the caller session; active member; at most 2 active keys per app, `client_key_limit`); the only exception are the seed's back-dated history keys (inserted with the admin secret through the same encrypt path, since `store_client_key` stamps now() and refuses past expiry; then revoked through `revoke_client_key`); revoked once by `revoke_client_key` (org_admin, flag `itap.client_key_context`); otherwise immutable except `last_used_at` (not audited).
- `authentication_sessions` (nonce_hash secret) and `authentication_attempts` (append-only, not audited) are written by the backend / engine and read by org_admin. ## Numbering and Codes

- Human-readable numbers: `number bigint NOT NULL` + `code text GENERATED ALWAYS AS ('PREFIX-' || lpad(number::text, 5, '0')) STORED`, `UNIQUE (organization_id, number)` and `(organization_id, code)`, and `BEFORE INSERT ... EXECUTE FUNCTION itap.assign_number('<entity>')` (per-organization counter in `organization_counters`). Never compute numbers in application code.

## Computed Fields

- Add `computedFields: [{ name, function }]` to a `TableSpec`; the function lives in `itap` and takes the table row. The generator only checks that the name does not clash with a column or another computed field of the table (it does not check that the function exists or clashes with relationship names; Hasura reports those on `make hasura_apply`).

## Transaction-Local Flags and Consent Effects

- Values only SQL functions may set (reserved enum values) are guarded by a trigger plus a transaction-local flag (`set_config('itap.merge_context','on',true)`), reset by the function before returning. Identity statuses `verified` / `pending_verification` use `itap.verification_context` the same way; that guard applies only to non-admin Hasura roles (the backend `actor`, admin secret and SQL are trusted).
- Side effects of a record (e.g. biometric consent -> `identities.matching_enabled`) are an AFTER trigger on the record table calling an idempotent `apply_*` function that takes the organization and subject ids and serialises with a row lock on the subject (`SELECT ... FOR UPDATE` of the profile row); reuse the pattern for other consent/permission-driven flags.

## Action Handlers

- `admin`: admin secret without a session; reads/lookups that must bypass permissions.
- `actor`: admin secret plus the caller's user/org session variables; use for every write so audit rows record the caller.
- `asCaller`: the caller's role; use when Hasura permissions should decide.

## Relationships

- Define relationships (object and array) in Hasura metadata for all foreign key associations.
- Use Hasura relationships for joins. Never write manual JOIN queries in application code.
- Name relationships clearly: singular for object relationships, plural for array relationships (e.g., `profile` vs `identities`).
- The generator names the reverse side after the child table; when the child's FK columns are its PK or a unique key (one-to-one) it is an object relationship (e.g., `organizations.organization_settings`).

## GraphQL Operations

- Use `graphql-codegen` to generate TypeScript types from the Hasura schema.
- Never write GraphQL response types by hand.
- Organize operations in `.graphql` files, co-located with the features that use them.
- Use fragments for reusable field selections.

## Naming Conventions

- Database tables: `snake_case`, plural (e.g., `identities`, `facility_areas`).
- Database columns: `snake_case` (e.g., `created_at`, `facility_id`).
- Enums: Hasura enum tables (`value text PRIMARY KEY, description text`, tracked with `isEnum: true`), never CHECK-constrained text; enum VALUES are lowercase `snake_case` (e.g., `org_admin`, `auth_success`).
- GraphQL root fields: Hasura defaults, `snake_case` (e.g., `organization_members`, `insert_organizations_one`, `update_organization_settings`); Nhost `auth`/`storage` tables keep their camelCase names (`users`, `insertFile`). Operation names are PascalCase (e.g., `SwitchOrgMembership`).

## Nhost Integration

- Use Nhost SDK for authentication and file storage.
- Nhost manages the Hasura instance -- do not configure Hasura independently of Nhost.
- Store uploaded images (face scans, profile photos) in Nhost Storage, reference by file ID in the database.
