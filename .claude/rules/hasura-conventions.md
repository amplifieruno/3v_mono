# Hasura and Database Conventions

## Data Access

- All data access goes through Hasura GraphQL. Never query PostgreSQL directly from application code.
- Use Hasura's generated GraphQL API as the single source of truth for CRUD operations.
- For complex business logic that cannot be expressed as Hasura actions, use custom Express handlers that are called via Hasura Actions or Events.

## Schema Management

- Schema changes are SQL migrations in `apps/nhost/nhost/migrations/default/`; apply with `make hasura_apply` (reset the dev DB with `make db_reset`).
- Metadata for tables in the `itap` schema is GENERATED by `pnpm --filter nhost metadata:generate` from the table definitions in `apps/nhost/metadata-src/`. Never hand-edit the generated `itap.*` metadata files; change the generator inputs and regenerate. Metadata for `auth`/`storage` tables and actions may still be edited by hand.
- `INFER_FUNCTION_PERMISSIONS` must stay `false`. Tracked SQL functions take a `hasura_session` argument where they depend on the session, and get explicit permissions.
- Tracked functions are GENERATED too: add a `FunctionSpec` to `functions` in `metadata-src/index.ts` (`exposedAs`, `sessionArgument: 'hasura_session'`, `customName`, `roles`); the generator writes `databases/default/functions/itap_*.yaml` and the `functions.yaml` include list, and checks the function exists, its session argument is `json` (and fails when a function has a `json hasura_session` argument the spec does not declare as `sessionArgument`), volatile functions are mutations, and every role can select the return table. A function with `roles: []` is callable only with the admin secret (e.g. `claim_invitation`, used by the `accept_invitation` action). Result row types live in `itap_results` (hide their root fields with `query_root_fields: []`).
- Mutation functions resolve every id inside `x-hasura-organization-id` (foreign ids raise the not-found code, nothing changes) and write explicit audit rows (`merge`, `rollback`, `approve`, `reject`) with the session `x-hasura-user-id`. Identity status `merged` and sources `merge`/`split` are reserved for the merge/rollback/split functions: a trigger rejects them unless the transaction-local flag `itap.merge_context` is `on`; functions that set it reset it before returning.

## Migrations

- Migration file naming: `{timestamp}_{description}` (e.g., `1707000000000_create_identities_table`).
- Each migration must be reversible -- include both `up.sql` and `down.sql`.
- One logical change per migration. Do not bundle unrelated schema changes.
- Test migrations locally before committing.

## Permissions

- Define all row-level and column-level permissions in Hasura metadata.
- Never implement permission checks in application code that duplicate what Hasura handles.
- Use Hasura roles to model access levels. Tenancy roles are `user` (base token: own memberships, `switch_organization`) and `org_admin` (org token, scoped to `x-hasura-organization-id`; its allowed roles are `[org_admin]` only, so it cannot renew itself). `public` (unauthenticated) sees nothing.
- Use session variables (`x-hasura-user-id`, `x-hasura-organization-id`) for permission filters.
- Rows that need someone's consent or a business check (memberships, invitations) get no direct insert permission; an Action creates them.

## Foreign Keys and Tenant Integrity

- Every tenant row carries `organization_id`. An FK between two tables that both have `organization_id` is composite: `(organization_id, x_id) REFERENCES t (organization_id, id)` (the parent needs a matching unique key), so a row can never point into another organization.
- Every FK column set has an index leading with `organization_id` plus the FK columns (a PK or unique key counts). Both rules are enforced by `metadata:generate`, which fails naming the constraint.
- `ON DELETE NO ACTION`, not `RESTRICT`, for references that an organization cascade removes in the same statement: NO ACTION is checked at statement end, RESTRICT fails mid-cascade.
- To null only the non-org column of a composite FK, use `ON DELETE SET NULL (x_id)` (PostgreSQL 15+); never null `organization_id`.
- `auth.users` rows are never deleted (disabled/anonymized), so FKs to them are `NO ACTION`.

## Reusable Triggers

- `updated_at`: `BEFORE UPDATE ... EXECUTE FUNCTION itap.set_updated_at()`.
- Audit: `CREATE TRIGGER audit AFTER INSERT OR UPDATE OR DELETE ... EXECUTE FUNCTION itap.audit_row_change('secret_col', 'ignore:system_col')` (plain args are redacted, `ignore:` columns are skipped). `audit_log.entity` is always the table name.
- File columns: `BEFORE INSERT OR UPDATE ... EXECUTE FUNCTION itap.check_file_bucket('photo_file_id', ...)` (file must be in the row's organization bucket). `organizations.logo_file_id` must be in the shared `org-logos` bucket.
- Assignment/recipient user columns: `BEFORE INSERT OR UPDATE ... EXECUTE FUNCTION itap.active_member_check('assignee_user_id', ...)` (active, unexpired member). Unknown column arguments raise `undefined_column`.

## Action Handlers

- `admin`: admin secret without a session; reads/lookups that must bypass permissions.
- `actor`: admin secret plus the caller's user/org session variables; use for every write so audit rows record the caller.
- `asCaller`: the caller's role; use when Hasura permissions should decide.

## Relationships

- Define relationships (object and array) in Hasura metadata for all foreign key associations.
- Use Hasura relationships for joins. Never write manual JOIN queries in application code.
- Name relationships clearly: singular for object relationships, plural for array relationships (e.g., `profile` vs `identities`).
- The generator names the reverse side after the child table; when the child's FK columns are its PK or a unique key (one-to-one) it is an object relationship (e.g., `organizations.organization_settings`).

## GraphQL Operations

- Use `graphql-codegen` to generate TypeScript types from the Hasura schema.
- Never write GraphQL response types by hand.
- Organize operations in `.graphql` files, co-located with the features that use them.
- Use fragments for reusable field selections.

## Naming Conventions

- Database tables: `snake_case`, plural (e.g., `identities`, `facility_areas`).
- Database columns: `snake_case` (e.g., `created_at`, `facility_id`).
- Enums: Hasura enum tables (`value text PRIMARY KEY, description text`, tracked with `isEnum: true`), never CHECK-constrained text; enum VALUES are lowercase `snake_case` (e.g., `org_admin`, `auth_success`).
- GraphQL root fields: Hasura defaults, `snake_case` (e.g., `organization_members`, `insert_organizations_one`, `update_organization_settings`); Nhost `auth`/`storage` tables keep their camelCase names (`users`, `insertFile`). Operation names are PascalCase (e.g., `SwitchOrgMembership`).

## Nhost Integration

- Use Nhost SDK for authentication and file storage.
- Nhost manages the Hasura instance -- do not configure Hasura independently of Nhost.
- Store uploaded images (face scans, profile photos) in Nhost Storage, reference by file ID in the database.
